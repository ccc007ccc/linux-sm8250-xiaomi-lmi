# lmi 硬件支持状态

本表记录 Redmi K30 Pro / POCO F2 Pro（lmi）在当前主线 Linux 适配中的硬件状态。状态只按已经在本项目镜像或主线代码路径中验证过的结果标记；未验证或只存在 Android downstream 参考的项目不视为已支持。

## 状态标记

- 已支持：当前主线镜像已验证基础功能可用。
- 部分支持：核心链路可用，但功能不完整或仍缺关键场景验证。
- 待适配：硬件已知，但当前主线镜像尚未接入。
- 暂不支持：当前阶段不计划支持，或主线路径缺失较多。

## 已验证的基础组合

- 控制台启动：UFS rootfs、DSI fbcon、USB ACM、Wi-Fi SSH 可同时工作。
- 输入显示：FT3518 触摸和 AMS667UU01 DRM/KMS 可同时工作。
- GPU：Adreno A650 / GMU / freedreno 可用于 GBM/EGL/GLES 渲染。
- 电源：PM8150B Type-C/TCPM、charger 和 fuel-gauge 普通路线可同时暴露 USB 输入与电池状态。
- 无线：Wi-Fi 使用真实 WLAN MAC，Bluetooth public address 使用 WLAN MAC + 1 的当前支持策略。

## 电池 / 充电当前结论

当前主线普通路线已接通 PM8150B Type-C/TCPM/VBUS、SMB5 charger 和 gen4 fuel-gauge。`/sys/class/power_supply` 已能看到 `pm8150b-charger`、`qcom-battery` 和 TCPM USB supply；M14 在标准 PD 电源上验证过 9V/2A，M15 验证 charger 在 USB online 时能通过 IIO 上报输入电压/电流。

仍未接入的是 Xiaomi 33W 私有快充、BQ2597x 充电泵、设备专用电池曲线、限充/停充策略和可能的硬件旁路供电控制。这些功能依赖更多私有策略或硬件能力，当前服务器使用目标先以稳定普通供电和电池状态可见为基线。

## 当前电源目标

lmi 作为长期运行服务器使用时，优先目标是稳定供电、电池状态可见、温度/安全信息可见。33W Xiaomi 私有快充和 BQ2597x 充电泵不是当前阶段目标；主线 Type-C/PD 路径能稳定协商 9V/2A 约 18W 即可。若只能以较低功率稳定供电，也先作为可接受基线记录，再逐步完善。Linux 没有通用“电源直供/绕过电池”开关；这类能力必须由 PMIC/charger 硬件和对应驱动暴露，当前 PM8150B 普通 charger 路径只确认了输入、电池和充电状态可见。

## 调制解调器当前诊断补充

M61 已验证 `mhi_sahara_diag.keep_prepared_on_release` 参数存在且默认关闭。keep-prepared 不能从测试开始就打开：这样会阻断此前依赖 SAHARA open/close reset 节拍推进出来的 image34/image40 请求，实测只得到 HELLO/HELLO_RESP 和后续空 session。当前正确策略是初始保持 `N`，等待真实 image40 `READ_DATA` 服务完成后，再由用户态 loader 切为 `Y` 以避免 release-time channel reset。

M61 还验证了 30 秒 idle timeout 过短：空 session close/reset 会触发 SAHARA chan2 RESET timeout，随后 SDX55M 进入 `SYS_ERROR`、PCIe D3cold/reset failed，并移除 `/dev/mhi_sahara0` / `/dev/mhi_bl0`。stock `vendor.img` 中 `/vendor/bin/ks` 确认 `DONE_RESP status=0` 属于 `SAHARA_MODE_IMAGE_TX_PENDING` / 继续等待 HELLO 的分支；但进一步把 `DONE_RESP status=0` 改成继续保持同一 fd 的实验也被证明不安全：干净重启后可完成 image34 两段传输并收到 `DONE_RESP 6 12 0`，但同 fd 90 秒内没有新 HELLO/image40，随后 close/reset 同样触发 chan2 RESET timeout 和 `SYS_ERROR`；因此 loader 默认已恢复为 DONE_RESP 后快速 restart。后续按 Android `ks` pending 语义测试 `DONE_RESP` 后才启用 keep-prepared，并在同一 fd 观察 75 秒，仍没有新 HELLO/image40；再开一次 session 90 秒也为空，设备保持 present，测试后 keep 已恢复为 `N`，loader 也已改为退出时恢复启动时的 keep-prepared 参数值。dmesg 同期出现一次 chan25 `BL` 48 字节 event / unexpected TRE，暂只作为 BL 通道线索，不视为 SAHARA image40 请求。后续 sideband watcher 验证中 GPIO 只保持 `gpio1=low gpio3=low gpio56=high gpio57=low`，没有 Sahara packet，连续多轮 90 秒空 session 后第 6 次 open `/dev/mhi_sahara0` 返回 `EIO` 并进入 `SYS_ERROR`/D3cold，说明失败或 DONE_RESP 后敏感状态不能继续消耗空 open/close 次数。当前 Sahara 测试脚本默认 timeout 保持 90 秒；后续用短状态采样或后台 watcher 管理等待，而不是缩短硬件实际需要的 session 节拍、在 DONE_RESP 后长期 hold fd，或在无包状态下重复打开关闭 SAHARA。当前 modem 仍只属于部分支持：Sahara image transfer 已推进到 live `mdmddr` image34 和 live `msadp` image40，但 Mission/AMSS、QRTR/QMI、SIM、语音和蜂窝数据仍未接入。

M62 补充：`KS_PENDING_TIMEOUT=75` 的同 fd pending 复测在干净启动后稳定复现到 image34 两段 live `mdmddr`、`END_OF_IMAGE` 和 host `DONE`，dmesg 确认 `DONE` 有 `UL completion status 0 bytes 8`，但 75 秒内没有收到 `DONE_RESP`；这与历史 M60/M61 的 `DONE_RESP` / image40 推进依赖 close/reopen/reset 节拍相矛盾，说明当前 `mhi_sahara_diag` 设备语义仍不同于 Android `/vendor/bin/ks` 使用的 `/dev/mhi_pipe_2` / UCI 路径。首轮全空 session 测试还暴露并修复了 `EMPTY_LIMIT=1` 在 `total_packets=0` 时不生效的问题；失败态或 DONE 后敏感状态不再重复消耗空 open/close，`SYS_ERROR` / D3cold 仍只用普通 Linux reboot 恢复。

M63 补充：新增默认关闭的 `mhi.sbl_accept_multi_tre_completion` 诊断开关后，M63 `#90` boot-only 镜像可正常启动，默认 `keep=N`、`multitre=N`。手动打开该开关并复测 `KS_PENDING_TIMEOUT=75` / `EMPTY_LIMIT=1` 时，Sahara 仍只推进到 image34 live `mdmddr`、`END_OF_IMAGE`、host `DONE`，同 fd 75 秒无 `DONE_RESP`；close/reopen 后可收到 `DONE_RESP 6 12 0`，但后续 75 秒无新 HELLO/image40，再一轮 90 秒空 session 后停止。dmesg 确认 chan25 `BL` 的 48 字节 event 命中 `SBL channel 25 accepting multi-TRE completion`，说明该开关能避免丢弃 BL multi-TRE completion，但不能单独解决 image40/`ks` pending 阻塞；测试后 `/dev/mhi_sahara0`、`/dev/mhi_bl0` 仍存在，参数恢复为 `N`，未触发 `SYS_ERROR` / D3cold。
